1Text is made of bytes UTF-8 · unicode1, unicode2

BeforeYou have text: letters, spaces, punctuation, maybe an emoji.
NowEvery character becomes 1 to 4 numbers between 0 and 255. These numbers are its UTF-8 bytes.
LaterThose 256 possible numbers become 256 tokens of your vocabulary. ID 0 is the special token <|endoftext|>, so byte b gets ID b + 1: the space (byte 32) is ID 33. Every token that training learns is glued together from these.

A computer stores text as numbers. Each character has a number in Unicode, its code point. UTF-8 writes that number as 1 to 4 bytes: English letters take one byte, other characters take more. A byte can only be 0 to 255, so there are just 256 kinds of "bricks", and any text in any language is a row of them. That is why a byte-level tokenizer never meets a word it cannot write down.

Why UTF-8, and why bytes must be read together

2Cut the text into word pieces split_on_special_tokens · PAT · count_pre_tokens · train_bpe

BeforeText: a Python string of characters. Section 1 showed how each character becomes bytes.
NowCut it twice: first at every <|endoftext|> (the border between two stories), then into word-sized pieces with GPT-2's pattern PAT. Then count how often each different piece appears, and store each one as its bytes: " sat" → ␣ s a t.
LaterTraining glues bytes only inside one piece, so no token ever spans two words. encode cuts new text the same way, with one difference: it keeps each <|endoftext|> as a piece of its own (ID 0), where training drops it.

The pieces are called pre-tokens. The space in front of a word stays with that word: " cat" is one piece, written ␣cat on this page so you can see the space. Punctuation and short endings like 't (from don't) and 'll (from I'll) become pieces of their own.

def count_pre_tokens(text, special_tokens):
    counts = Counter()
    for piece in split_on_special_tokens(text, special_tokens):  # 'the cat sat.', then 'the hat sat.'
        for match in regex.finditer(PAT, piece):                  # 'the', ' cat', ' sat', '.'
            pre_token = match.group()
            counts[pre_token] += 1                                # counts[' sat'] (= 2) after both stories
    word_counts = {}
    for pre_token, count in counts.items():
        word = tuple(bytes([b]) for b in pre_token.encode("utf-8"))  # ' sat' -> (b' ', b's', b'a', b't')
        word_counts[word] = count
    return word_counts                                            # 5 different pieces (= 8 pieces in all)

def count_pre_tokens_in_file(input_path, special_tokens):
    num_processes = os.cpu_count() or 1                          # 16
    if special_tokens:
        with open(input_path, "rb") as f:
            boundaries = find_chunk_boundaries(f, 4 * num_processes, special_tokens[0].encode("utf-8"))
            # special_tokens[0] (= "<|endoftext|>"): 65 positions -> 64 chunks
    else:
        boundaries = [0, os.path.getsize(input_path)]
    jobs = [(input_path, start, end, special_tokens) for start, end in pairwise(boundaries)]
    if len(jobs) <= 1:
        results = [_count_chunk(job) for job in jobs]            # one chunk: no workers needed
    else:
        with multiprocessing.get_context("forkserver").Pool(min(num_processes, len(jobs))) as pool:
            results = pool.map(_count_chunk, jobs)               # 64 dicts of counts
    total = Counter()
    for word_counts in results:
        total.update(word_counts)                                # 59,933 different pieces
    return dict(total)

def train_bpe(input_path, vocab_size, special_tokens):           # vocab_size (= 10_000)
    word_counts = count_pre_tokens_in_file(input_path, special_tokens)
    number_of_merges = vocab_size - len(special_tokens) - 256    # 10,000 - 1 - 256 = 9,743
    merges = learn_merges(word_counts, number_of_merges)
    vocab = build_vocab(special_tokens, merges)                  # 10,000 entries
    return (vocab, merges)

def _encode_pre_token(self, pre_token):                 # pre_token (= " accomplishment")
    word = tuple(bytes([b]) for b in pre_token.encode("utf-8"))  # 15 single bytes
    while True:
        best_pair, best_rank = None, NEVER          # NEVER (= float("inf")): the rank of a pair never learned
        for pair in pairwise(word):
            rank = self.ranks.get(pair, NEVER)          # (b' ', b'a') -> 2, (b'o', b'm') -> 27, (b'c', b'c') -> 7690
            if rank < best_rank:
                best_pair, best_rank = pair, rank       # best_pair (= (b' ', b'a')), best_rank (= 2)
        if best_pair is None:                           # no learned pair left
            break
        word = merge_pair(word, best_pair)              # the merge_pair training uses: (b' a', b'c', b'c', b'o', ...)
    return [self.ids[token] for token in word]          # [7160]  (your code uses a loop)

Part 2 adds a memory to this function: the first time a piece appears, this loop runs and the answer is stored; every later time it is one lookup. Same IDs, 4.1 times faster. Section 10.

def encode_iterable(self, iterable):
    buffer = ""                                         # the held-back piece
    for chunk in iterable:                              # "the ca", then "t sat."
        pieces = self._pieces(buffer + chunk)           # ['the', ' ca'], then [' cat', ' sat', '.']
        if pieces:
            buffer = pieces.pop()                       # ' ca', then '.'
        for token_id in self._encode_pieces(pieces):    # 259 (= the, small tokenizer), then 33 100 257 33 116 257
            yield token_id
    last_pieces = self._pieces(buffer)                  # ['.']
    for token_id in self._encode_pieces(last_pieces):   # 47
        yield token_id

Three ways to collect results from a pool of workers

A pool is a group of worker processes. You hand it a list of jobs (here, chunks), and each free worker takes the next one. The three methods differ only in how the results come back to your main process.

For counting, order does not matter: adding the counts in any order gives the same total. Here the chunks finished in the order 3, 0, 6, 4, 5, 1, 7, 2, 8, 10 …, and the total was 627,486 different pieces either way. For encoding, order does matter: section 12.

TinyStories train59,933different pieces in 2,227,753,162 bytes (536,592,168 pieces)

The small web file is 13% the size of TinyStories train, yet it has 10.5 times as many different pieces: names, numbers, links, other languages. Every different piece is a key in the counts, so the counts of web text take far more memory. Chunks of at most 32 MiB keep each worker's share small, and imap_unordered keeps the main process from holding them all at once.

CHUNK_BYTES = 32 * 1024 * 1024                         # 33,554,432: the most one worker reads at once

def count_pre_tokens_in_file(input_path, special_tokens):
    num_processes = os.cpu_count() or 1                 # 16
    file_size = os.path.getsize(input_path)             # 11,920,511,059 (owt_train.txt)
    if special_tokens:
        num_chunks = max(4 * num_processes, file_size // CHUNK_BYTES)   # max(64, 355) = 355
        with open(input_path, "rb") as f:
            boundaries = find_chunk_boundaries(f, num_chunks, special_tokens[0].encode("utf-8"))
    else:
        boundaries = [0, file_size]
    jobs = [(input_path, start, end, special_tokens) for start, end in pairwise(boundaries)]
    total = Counter()
    if len(jobs) <= 1:
        for job in jobs:
            total.update(_count_chunk(job))
    else:
        with multiprocessing.get_context("forkserver").Pool(min(num_processes, len(jobs))) as pool:
            for word_counts in pool.imap_unordered(_count_chunk, jobs):   # owt_valid: chunk 3 first, then 0, 6, 4 …
                total.update(word_counts)               # add it now; this chunk's counts can then be freed
    return dict(total)                                  # owt_valid: 627,486 different pieces

The small example, through encode_file with the 3-merge tokenizer

To get more than one chunk from 37 bytes, this demo passes chunk_bytes=8. The real files use 4 MiB.

Each ID takes 2 bytes, the smaller byte first (little-endian): 259 = 1 × 256 + 3, so it is written 03 01. The file has no header: just 17 IDs × 2 bytes = 34 bytes. That is why np.memmap(path, dtype=np.uint16) can read it back with nothing else to know.

Why cut before <|endoftext|>, and why keep the file order

Part (d): why uint16

Your TinyStories files, encoded

Read back with np.memmap: the largest ID in the train file is 9,999, and ID 0 (<|endoftext|>) appears 2,717,699 times, once per story. Its first IDs, 11, 430, 439, 259, 398, 401 …, decode to ↵Once upon a time there was a little boy named Ben. Ben loved to explore the world around …

One worker encoding one 16 MiB chunk peaked at 336 MB: its lists of 4 million pieces and 4 million IDs take far more room than the text. 16 such workers need about 5.4 GB, while the OpenWebText training was using 9 GB of this machine's 15.5. So CHUNK_BYTES is now 4 MiB: 111 MB per worker, the same IDs, since every cut still sits before an <|endoftext|>.

def _encode_chunk(job):                                 # job (= (path, 0, 4,195,665)): chunk 0
    input_path, start, end = job
    with open(input_path, "rb") as f:
        f.seek(start)
        text = f.read(end - start).decode("utf-8")
    return np.array(_worker_tokenizer.encode(text), dtype=np.uint16)   # 1,020,766 IDs
